## 1. 제품 개요

### 한 줄 요약
Figma 디자인을 읽어 shadcn/ui 코드로 만들고, **실제 브라우저 검증을 통과해야만 "완료"가 되는** Claude Code 디자인 자동화 킷. (Phase 3에서 마케팅 소재 자동화 — SNS·배너·명함 등 — 로 확장)

### 해결하는 문제
- RESEARCH_SOURCES 자료(-01~-03)에는 좋은 도구가 100개+ 정리되어 있지만, **도구 목록일 뿐 실행 순서를 강제하는 장치가 없다.** 매번 사람이 "Figma 읽어줘 → 코드 짜줘 → 검증해줘"를 기억해서 시켜야 한다.
- AI가 만든 UI는 검증 없이 "완료"라고 보고되는 일이 잦다(원천 자료 23번이 직접 경고한 약점).
- 이 킷은 자료의 핵심 조합(Figma MCP + shadcn/ui + Playwright + 접근성 검사)을 **한 번의 명령으로 실행되는 고정 파이프라인**으로 묶고, 검증 실패 시 완료를 차단한다.

### 핵심 가치 (기존 대안과의 차이)
| 기존 대안 | 한계 | 이 킷의 차별점 |
|------|------|------|
| 공식 Figma 플러그인 (Claude Code) | 디자인 읽기/쓰기만 — 검증 없음 | 생성 **후** 검증 게이트까지 한 파이프라인 |
| storybook-assistant, playwright-skill (개별 오픈소스) | 각각 한 단계만 담당 | 단계들을 **고정 순서로 연결** + 판정서 기록 |
| Superdesign 등 워크플로우 가이드 | 문서일 뿐 강제성 없음 | 훅으로 **완료 차단을 기계적으로 강제** |
| v0/Lovable 등 AI 빌더 | 외부 SaaS, 내 코드베이스 밖 | 내 프로젝트 안에서, 무료 도구만으로 작동 |

> 원천 자료 장점 극대화: 자료 18-1(Figma→Code 워크플로우)·19번(AGENTS.md 규칙)·23번(주의사항)을 그대로 킷의 실행 규칙으로 인코딩한다.
> 원천 자료 단점 보완: "목록은 있으나 실행층이 없다"는 공백을 킷이 채운다.

## 2. 사용자

### 주요 사용자
- **누구**: 비개발자 바이브코더(본인). Claude Code로 웹 프로젝트를 만들지만 UI 품질 검증을 매번 수동으로 시키는 사람.
- **상황**: 새 화면/컴포넌트를 만들 때, 또는 기존 UI를 Figma 시안에 맞출 때.
- **목표**: "디자인 그대로, 접근성·반응형까지 통과된 코드"를 명령 한 번으로 얻는다.

### 사용자 시나리오
1. 사용자가 프로젝트에서 `/design-kit` 설정 명령으로 config.json을 만들고
2. Figma 링크(또는 요구사항)를 주며 파이프라인 명령을 실행하면
3. 킷이 디자인 컨텍스트 읽기 → 컴포넌트 매핑 → shadcn/ui 코드 생성 → Playwright 실브라우저 + 접근성 + 3개 뷰포트 검사를 자동 수행하고
4. `reports/`에 PASS/FAIL 판정서가 남으며, FAIL이면 완료로 표시되지 않는다.

### 기능×표면 등가성(Parity) 매트릭스 (2026-07-20 18차 — "어디서 써도 같은 코어" 계약)

> 원칙: **모든 표면(터미널 명령·대시보드·MCP 래퍼·AGENTS.md)은 같은 코어 엔진(`scripts/*.mjs`)을 호출하는 얇은 래퍼다** (03 "코어/래퍼 분리 원칙"의 계약 승격). 같은 입력 → 같은 코드 → 같은 판정. 표면이 코어를 우회해 자체 판정·자체 상태 쓰기를 하는 것을 금지(04 DO NOT·02 데이터 계약 연동).

| 등급 | 기능 | CC 터미널(P1) | Codex(P1) | 대시보드(P2) | Claude 데스크탑 MCP(P3) | GPT 데스크탑 |
|---|---|---|---|---|---|---|
| **T1 코어** — 결정적 Node 작업, 표면 무관 100% 동일 | 검증 실행·재검증·판정서/이력/스크린샷 열람·component-map 조회·setup | O | O | O (열람+트리거) | **O (구현 완료 2026-08-20)** | 조건부 승격 |
| **T2 AI 작업** — AI 클라이언트 필요 | Figma 읽기→매핑→코드 생성 | O | 규칙 수준 | X (대시보드는 AI가 아님 — 정직 고지) | **T2a만 O (구현 완료 2026-08-20), T2b는 보류** | 조건부 |
| **T3 플랫폼 훅** | 완료 차단 | **O (유일)** | X | X | X | X |

- T1은 "완벽하게 동일"이 기술적으로 보장되는 범위 — 어느 표면이든 같은 `.mjs` 코드가 실행되므로 표면별 차이가 원천적으로 없다.
- **정정(2026-08-20 실측)**: "MCP 래퍼가 대시보드와 같은 로컬 서버를 공유한다"는 원안 전제는 실제로는 성립하지 않는다 — Claude Desktop의 로컬 MCP는 HTTP가 아니라 stdio(서브프로세스+stdin/stdout) 전송이라 리스닝 포트를 열지 않는다. "서버 공유"가 아니라 대시보드가 이미 export한 함수를 MCP 서버가 in-process로 그대로 재사용하는 방식으로 T1 동등성을 달성했다(상세는 `02_DATA_MODEL.md` 결정 기록).
- **정정 2건째(2026-08-20, T2 착수 스파이크 실측)**: "Figma 읽기→매핑→코드 생성"을 한 덩어리 능력처럼 표기한 원안도 정확하지 않았다 — 이 킷엔 "Figma 데이터를 받아 코드를 생성하는 함수"가 애초에 없다(Claude Code용 `commands/pipeline.md`도 코드 작성은 항상 에이전트 자신의 몫으로 설계돼 있음). `pipeline-codegen.mjs`는 위험 등급이 다른 두 경로를 제공한다: **T2a** `runCodegen()` — 이미 매핑된 컴포넌트를 dev 전용·gitignore 대상 프리뷰 라우트에 연결만(신규 코드 0줄, T1과 같은 등급의 위험) — **T2b** `registerNewComponent()` — 실제 애플리케이션 코드를 프로젝트에 새로 씀(Claude Desktop엔 완료 차단 훅이 없어, 이 경로를 그대로 MCP로 열면 검증 없이 실제 코드가 조용히 프로젝트에 들어갈 수 있는 첫 통로가 됨 — 01 §1 핵심 가치와 직접 충돌). 이번 증분은 T2a만 `register_component_preview` 도구로 노출했다. **T2b는 별도 리스크 검토·별도 사용자 승인 없이는 착수하지 않는다.**
- T2·T3는 물리적 한계(대시보드에 AI 없음·타 클라이언트에 Stop 훅 없음)라 동일 불가 — **되지 않는 것을 동일하다고 표기하지 않는다**(검증 게이트 정신과 동일한 정직 원칙).

## 4. 사용자 흐름 (User Flow)

### 핵심 흐름
```
설정 마법사 → Figma 링크 입력 → 디자인 읽기 → 컴포넌트 매핑
→ 코드 생성 → [검증 게이트: 브라우저+접근성+반응형] → PASS 판정서 → 완료
                                    ↓ FAIL
                              자동 수정 재시도 (최대 N회) → 재검증
```

### 상세 흐름
1. **설정**: 프로젝트당 1회. Figma 파일 URL·프레임워크·뷰포트를 config.json에 저장.
2. **생성**: 컴포넌트 1개 단위로 시작(원천 자료·유사 사례 공통 권고: "작게 시작"). component-map.json에 기존 컴포넌트가 있으면 재사용 우선.
3. **검증**: verify-runner가 dev server 자동 기동(포트 충돌 시 다음 포트로 자동 우회) → Playwright 실제 렌더 → axe-core 위반 검사(게이트 판정 기준) → 3개 뷰포트 스크린샷. Lighthouse 점수는 참고 지표로 별도 기록.
4. **판정**: reports/*.md에 PASS/FAIL과 근거(위반 건수·점수·스크린샷 경로) 기록. FAIL이면 훅이 완료 보고를 막는다. 재시도 시에는 판정서의 실패 사유(axe 위반 항목·콘솔 에러)를 다음 생성 시도에 주입한다(**실패 피드백 주입** — 같은 실패 반복 방지).

## 5. UI/UX 요구사항 (2026-07-19 보강)

> 적용 대상 2종 구분: **(A) 파이프라인이 생성하는 코드**(이 킷의 산출물 — 대부분의 기준이 여기 적용) / **(B) 킷 자체 화면**(P1 프리뷰 라우트·P2 open 대시보드).
> 집행 방식: 대비·폼 라벨 등 접근성 기준은 **기존 게이트(axe critical/serious)가 이미 자동 검사** — 게이트 확장 없음(PASS 조건 4종 불변, 02가 단일 출처). 나머지는 04의 생성 규칙(DO NOT/ALWAYS DO)으로 강제.

### 디자인 방향
- 심플·모던·자연스러움 — **실제 서비스 수준의 완성도** 기준, 데모용 화려함 배제
- shadcn/ui 기본 미학(중립 팔레트·낮은 채도·명확한 위계)을 그대로 따름 — 킷이 새 스타일을 발명하지 않는다

- **open 대시보드(P2)**: 단일 페이지 정보 구조 — 최신 실행이 최상단, PASS/FAIL은 색+텍스트+아이콘 병기, 스크린샷 3종은 뷰포트 라벨과 함께 나란히 비교, 실패 사유는 스크롤 없이 보이는 위치. 폼 없음 — 액션은 **재검증 트리거 버튼 1개**(T1·실행 중이면 `.lock` 안내로 비활성)와 새로고침·필터뿐(2026-07-20 18차 — 상태 편집 UI는 계속 금지)

### 해당 없음 — 없는 것을 없다고 명시 (공격면 최소화가 곧 설계)

- **로그인/세션/JWT/권한 분리(관리자·일반·비로그인)**: 계정 체계 자체가 없음(로컬 1인용·로그인 불필요 확정). 유일한 접근 통제 = 로컬 서버의 127.0.0.1 바인딩 + 실행별 토큰

- **SQL Injection·결제 보안**: SQL·결제 코드가 존재하지 않음
- **부활 조건**: P3에서 구독 서비스화가 확정되는 순간 위 항목 전부 필수로 부활 — 그 시점에 OWASP ASVS 기준 보안 섹션 재작성을 **착수 게이트**로 한다
